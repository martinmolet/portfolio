Retail banking Case study 01 / 03

Société Générale× Devoteam

Scaling the AVENIR Design System, the library that runs retail banking.

Role
Consultant Design System Manager
Period
Mar 2024 — Sep 2025 · 18 months
Team
40+ Product Designers · 3 domains
Stack
Figma · Variables · Zeroheight · Storybook
Context

When I joined Société Générale, the AVENIR DS had been live for three years. Solid, but running out of steam: a single designer for 40+ users, no governance, and a volume of requests that blocked any evolution.

My contribution
Governance · Tokens · Components · Training
The team
1 DSM · 1 senior PD · 3 product domains
Scope
Retail · Insurance · Advisory
Releases
4 releases shipped in 18 months
01
Communication

Smoothing the exchanges between the DS team and 40+ designers.

Requests came in directly, unfiltered. Every question disrupted the work cycle, every issue escalated live. The DS team spent more time managing the flow than moving the system forward.

We set up dedicated channels, weekly rituals and a Jira ticketing system, so every request had a clear path.

The weekly OpenHours became an open space for designers, POs and devs. Experienced members gradually took on a DS ambassador role. The community formed naturally around the system.

02
Library

Reorganizing the Figma library so anyone can navigate it without prior knowledge.

Components were grouped by logical family, which meant you had to know the internal taxonomy to find them. A complex onboarding and daily friction for every designer.

We restructured the library alphabetically, aligned with the Storybook sidebar. One page per component, clear separators. Figma and code finally speak the same language.

03
Size tokens

280+ variables created to set a single source of truth for dimensions.

When I arrived, almost no size tokens existed. Everything was hard-coded, screen by screen: spacing, grids, radius, typography. Every mobile/desktop variant was manual work.

With the right tokens, the same screen renders in two modes in seconds. Producing screen variants became 4× faster.
  • 280+Variables created: screen sizes, spacing, grids, radius, typography
  • 1Same spacing tokens for mobile and desktop, one single source
  • 4×Faster screen variants once the tokens were in place
04
Color tokens

230+ variables to go from two libraries to a single themed one.

Historically, colors had no usage contract. Any color could go anywhere. The result: two identical libraries maintained in parallel, one for client mode, one for advisor mode.

We reorganized everything: a palette with distinct functions (status, brand, ui), semantic tokens with aliases, and a system of Figma modes. Switch client ↔ advisor in one click.

05
Components

185+ components rebuilt or created: clear scope, slots, variables.

Every rebuilt component follows the same logic: define a strict scope, use slots for flexibility, drive responsive behavior with variables. Three representative examples.

Header and footer lived in a single component. Their properties got mixed up (sidebar, header, footer) and caused display errors on every use. Splitting them made each component readable and maintainable on its own.

The old Layout had to anticipate every possible combination. With slots, one component covers every case: designers drop in what they need without creating a new variant. Responsive behavior is driven automatically by variables.

  • EX.01Header & footer split: clear properties, zero conflicts
  • EX.02Layout slots: one component for every case (tabs, stepper, empty)
  • EX.03Automated patterns: variants in one click, redundant variants removed
06
Support & training

A DS only exists if it’s used. 40+ designers trained, a community built.

Every release came with live tutorial sessions. Every component was documented in three formats: Figma for designers, Storybook for developers, Zeroheight for long-form reading.

Designers no longer opened the DS to copy components. They used it to think through their work.
